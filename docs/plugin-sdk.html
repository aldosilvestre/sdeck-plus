Start here

Overview

A plugin is a small external program. The app starts it once for every key press or dial event that is bound to one of its actions, hands it one JSON request and reads back one JSON answer. Nothing keeps running in between.

What a plugin is

  • Any language. A plugin is an executable file plus a manifest.json. It reads one line from stdin and writes one line to stdout, so a shell script, Python, Go or Rust binary all work. The template and both reference plugins use Python 3 and its standard library only.
  • One request per process. Each press, dial turn, dial press or touch event starts a fresh process, which exits when it has answered. Keep no state in memory; keep any state in files you own.
  • Actions come from the manifest. The app reads manifest.json only, lists the actions in the Actions catalog under a Plugins heading, and builds the settings form from the field definitions. Your code never draws a window.
  • Runs sequentially on its own worker. Plugin requests are queued (eight waiting at most) and run one at a time with a fixed 5 s deadline each, so a slow plugin cannot delay built-in actions. Every dial event starts a process, so bind a dial turn only to an action that is cheap and quick.

Trust model

A plugin runs with your user's privileges. Process separation is not a sandbox. It can read your files and use your network like any program you start. The app therefore never enables a plugin by itself: it is disabled by default, and the user must tick Enable after reading the warning. Saving a binding never runs a plugin; only Test action or the physical control does. The app never installs packages or changes permissions for a plugin, and a missing dependency never blocks enabling. Write your plugin so that a user who reads run finds nothing surprising.

Ten minutes

Quick start

Start from the template in examples/plugin-template of an sdeck-plus checkout. It defines an hello plugin with one action, say-hello, that only returns a greeting.

From a copy to a working action

  1. Create the project. Copy the template out of the checkout and make it its own repository: 
    cp -r examples/plugin-template ~/src/sdeck-plugin-greeter
cd ~/src/sdeck-plugin-greeter && git init
  2. Edit manifest.json. Set id (here greeter), name, version, your actions with their settings, and the requirements your code needs. See the reference.
  3. Write run. Keep the framing of the template (one request line in, one response line out, failures as ok:false) and replace the action. Keep it executable (chmod 755 run).
  4. Validate it without running it. From the sdeck-plus checkout: 
    cargo run --offline --example plugin_validate -- ~/src/sdeck-plugin-greeter
    It prints PLUGIN_VALIDATE_OK: with the actions and requirements, or one PLUGIN_VALIDATE_ERROR: line per problem.
  5. Optionally run one action. This runs your plugin once with your privileges: 
    cargo run --offline --example plugin_validate -- ~/src/sdeck-plugin-greeter \
  --invoke say-hello --settings '{"name":"Ada"}'
  6. Install it. The folder name must equal the manifest id: 
    dest="${XDG_DATA_HOME:-$HOME/.local/share}/sdeck-plus/plugins/greeter"
mkdir -p "$dest"
cp manifest.json "$dest/" && install -m 755 run "$dest/run"
  7. Enable and test it in the app. Press Update plugins (the icon at the right end of the binding toolbar), open the plugin under Plugins in the Actions catalog, tick Enable, assign an action to a control, fill in the form, Save binding and press Test action. The result appears in the status line.

Structure

Project layout and repository conventions

One repository per plugin. A new plugin is a new project, not a folder inside sdeck-plus.

Files

sdeck-plugin-<id>/
├── manifest.json     # required at runtime
├── run               # required at runtime: the executable named by the manifest
├── README.md         # what it does, a Dependencies section, install steps, limits
├── LICENSE
└── tests/            # your unit tests (development only)
  • Name: sdeck-plugin-<id> is the suggested repository name, where <id> is the manifest id (the installed folder is named after the id, not the repository).
  • At runtime only two files matter: manifest.json and the executable. Everything else is for development. Copied by hand, an installed plugin is just those two files in plugins/<id>/; the app's Add plugin dialog copies the whole project instead (without .git and __pycache__), so helper files next to the executable arrive too. The executable may be any relative path inside the plugin folder (run by convention), but it must stay inside it.
  • Repository root. To be installable from an https:// address, manifest.json and the executable must be at the top level of the repository (see the repository rules).
  • README.md states what each action does, the Dependencies table, the credential files the user must create, install and test commands, and honest limits (see the checklist).
  • Add a .gitignore for __pycache__/ and *.pyc, and keep secrets and tokens out of the repository.

Reference

manifest.json reference

At most 64 KiB. Unknown fields are rejected at every level, so a typo is an error, not a silent no-op. Parsing the manifest never launches your executable.

Example

{
  "id": "hello", "version": "0.1.0", "protocol_version": 1, "name": "Hello",
  "executable": "run",
  "requirements": [
    {"kind": "command", "name": "python3", "version": ">= 3.8"}
  ],
  "actions": [{
    "id": "say-hello", "name": "Say hello", "description": "Returns a greeting.",
    "controls": ["key", "dial_press"],
    "settings": [
      {"type": "text", "id": "name", "label": "Name", "max_length": 32, "default": "world"},
      {"type": "boolean", "id": "shout", "label": "Shout", "default": false}
    ]
  }]
}

Top-level fields

FieldTypeRule
idstring, required1-48 characters of [a-z0-9_-], starting with a letter or digit. Must equal the plugin's folder name once installed.
versionstring, required1-32 printable characters. Free text (semantic versioning is recommended); shown as v<version>.
protocol_versioninteger, requiredMust be 1.
namestring, required1-64 printable characters, not blank. The sidebar title.
executablestring, requiredPlain relative path, at most 128 characters, no .., no absolute path. It must resolve (symlinks included) to an executable regular file inside the plugin folder; this is checked at discovery and again at every run.
actionsarray, required1 to 32 actions, unique ids.
requirementsarray, optionalDefault none; at most 16. See Declaring dependencies.

The app lists at most 64 plugin folders; the rest are reported as skipped.

Actions and controls

FieldTypeRule
idstring, requiredSame rule as the plugin id; unique within the plugin. This is what the request's action carries.
namestring, required1-64 printable characters, not blank.
descriptionstring, optionalAt most 256 characters.
controlsarray, requiredAt least one of key, dial_turn, dial_press, touch (the touch strip). The editor only lets the user assign the action to controls listed here.
settingsarray, optionalDefault empty; at most 16 fields, unique ids. See below.

Setting field types

Every field has type, id (same rule as other ids, unique within the action), label (1-64 printable characters, shown in the form) and required (default false), plus:

TypeExtra fieldsAccepted value
textmax_length (default 256, 1-1024), default (string)A string of at most max_length characters with no control characters. When required it must not be blank. The saved binding keeps text up to 1024 characters.
integermin and max (both mandatory, min ≤ max), default (integer)A 64-bit integer within [min, max]; the form shows a bounded number field.
booleandefault (boolean)true or false; the form shows a check box.

A default must itself satisfy the field's limits, or the manifest is rejected. There are no other field types: a list, a secret or a file picker is not available, which is deliberate (see Security).

Reference

Settings and the editor form

The user fills in a form the app generates from your field definitions. The values travel with the binding and reach your plugin in the request.

Who validates what

  • The host validates first. Before it starts your process it checks the settings against the manifest: unknown keys, wrong types and out-of-bound values are rejected; defaults are filled in; a missing required field without a default is rejected; the serialized payload must fit in 4096 bytes. A rejected binding never starts the plugin.
  • The plugin MUST validate again. Treat the settings as untrusted input anyway: someone can run your executable by hand, a future host build could differ, and a bug on either side must not become a command injection. Check every key and type, apply your own defaults and refuse anything unexpected with ok:false.
  • Absent is possible. An optional field with no value and no default is omitted from settings. Do not assume a key exists.
  • Unknown settings are rejected, never ignored. Reject them in your plugin too, so a misspelled key is reported rather than silently dropped.
  • Settings are stored in plain text. They are saved in layers.conf and exported in bundles. Never ask for a password or token as a setting (see Security).

Contract

Protocol v1

One request line on stdin, one response line on stdout, exit status 0. Anything else is an error the user sees.

Request and response

The host writes one JSON line to stdin, then closes it (EOF):

{"protocol_version":1,"type":"invoke","request_id":"sdeck-7","action":"say-hello","settings":{"name":"Ada","shout":false}}

Your plugin answers with exactly one JSON line on stdout, then exits with status 0:

{"protocol_version":1,"request_id":"sdeck-7","ok":true,"message":"Hello, Ada!"}
{"protocol_version":1,"request_id":"sdeck-7","ok":false,"error":"name must be non-empty text"}
  • request_id is echoed unchanged. It is 1-64 characters of [A-Za-z0-9._-] chosen by the host (the app uses sdeck-N). A different value is an error.
  • Required response fields: protocol_version (1), request_id and ok. Optional: message and error, strings of at most 512 characters. Unknown response fields are rejected. On success the message is shown in the status line; on failure the error is (without one the user sees "plugin reported failure").
  • Exactly one stdout line, UTF-8, no banner, no progress output, no second JSON object. Blank lines are ignored; any other extra line is an error.
  • stderr is for diagnostics only: the first 4096 bytes are kept and shown with a non-zero exit. Never write secrets or the user's message text there.
  • Exit status 0, even for failure. Report failures as ok:false with a helpful error. A non-zero exit is treated as a crash and its stdout is not used.
  • Always answer. Catch unexpected exceptions, answer ok:false with a generic message and never print a traceback to stdout. If the request cannot be parsed, answer with its request_id when you can still read it.
  • Read one line, bounded. The request is a single line; read it with a size bound instead of reading until a stream you do not control ends.

What the host does with each outcome

These are the PluginError values of the host. The app shows them on the status line as Plugin <id>/<action> failed: <message> (request <request_id>).

OutcomeWhenMessage shown
ReportedYou answered ok:falseplugin reported an error: <your error>
NonZeroExitExit status is not 0 (checked before stdout is read)plugin exited with Some(1): <stderr>
MalformedResponseStdout is not UTF-8, is empty, has more than one line, is not the JSON shape above, has another protocol_version, or a text over 512 charactersmalformed plugin response: <detail>
RequestIdMismatchThe echoed request_id differsplugin answered a different request
OutputTooLargeStdout grows beyond 16 KiB (the process is killed)plugin output exceeded the size limit
TimeoutSpawn, exchange and exit take longer than the deadline (the process group is killed)plugin timed out

Before any process starts, the host can also refuse the request: the plugin is not installed (Missing), disabled (Disabled), no longer offers the action (UnknownAction), the settings do not fit (InvalidSettings), the executable is missing, not executable or resolves outside the plugin folder (UnsafeExecutable), or the process cannot start (Spawn). A request is never retried by the host.

Reference

Limits and environment

The numbers below are enforced by the host today. They are the public constants of sdeck_plus::plugins where one exists.

Limits

WhatLimit
manifest.json64 KiB
Settings payload (serialized, defaults included)4096 bytes
One saved text setting1024 characters (and at most 16 settings per binding)
Your stdout16 KiB; more kills the process (OutputTooLarge)
Your stderr4096 bytes kept, the rest is read and dropped
message and error512 characters each
Request deadlineCovers spawn, exchange and exit. The host API defaults to 5 s and accepts at most 60 s (the validator's --timeout). The app always uses a fixed 5 s deadline today. A manifest cannot yet ask for a longer deadline, so design every action to finish well within 5 s.
QueueEight requests wait behind the one running; a ninth is refused with a status message. Requests run one at a time.
ShutdownQueued requests are dropped; a running one is waited for at most 6 s.
Counts64 plugins, 32 actions per plugin, 16 fields per action, 16 requirements; ids up to 48 characters

The process you get

  • Cleared environment. Your process starts with an empty environment plus only these eight variables, and only when the app itself has them set: PATH, HOME, LANG, XDG_RUNTIME_DIR, XDG_CONFIG_HOME, XDG_DATA_HOME, WAYLAND_DISPLAY, DBUS_SESSION_BUS_ADDRESS. Any of them can be absent, so read with a fallback.
  • Everything else must be derived. Nothing else is inherited. Example: Hyprland's HYPRLAND_INSTANCE_SIGNATURE is not forwarded, so a plugin that calls hyprctl must find the running instance itself (the Discord reference plugin looks in $XDG_RUNTIME_DIR/hypr/). Never ask the user to add variables to the app's environment.
  • Working directory is the plugin's own folder. Do not rely on it for user data.
  • No shell and no terminal. stdin carries the request, stdout the response, stderr the diagnostics.
  • Own process group, killed afterwards. The process runs in its own group. When it exits, times out or errors, the host kills the whole group and reaps it, so background children do not outlive the request. Do not try to daemonize; a descendant that creates its own session can escape, which is a limit of process groups, not a promise.

Responsibility

Security and credentials

The host bounds time, output and file layout. Everything your plugin does with the user's account is your responsibility.

Rules for plugin authors

  • Process separation is not a sandbox. Your code can do anything the user can. Say in your README what it touches, and keep that small.
  • Never put secrets in bindings or settings. Bindings are saved in plain text in layers.conf and exported in configuration bundles. Tokens, passwords and API keys never belong in a settings field, a default or the manifest.
  • Use the token-file pattern. The user creates a file you document, for example $XDG_CONFIG_HOME/sdeck-plus/plugins/<id>/token (falling back to $HOME/.config/...). Before using it, require a regular file (not a symlink) owned by the user with no group or other permissions (mode 0600), and bound its size. On failure name the path and the rule, never the contents. Document the creation: 
    mkdir -p ~/.config/sdeck-plus/plugins/<id>
install -m 600 /dev/null ~/.config/sdeck-plus/plugins/<id>/token
$EDITOR ~/.config/sdeck-plus/plugins/<id>/token   # paste the token only
  • Argument lists, never a shell. Start subprocesses with an argv list and no shell (subprocess.run([...]) without shell=True). Never build a command string from settings.
  • Validate untrusted input before any subprocess or file or network access: allow-list characters, bound lengths, reject control characters, and check the action name.
  • Bound time and output. Give every subprocess, connection and read its own timeout inside your 5 s budget, and cap what you read back.
  • Never echo secrets. Not in message, error or stderr. The response text appears in the status line and may be logged by the user's tools; keep the user's own message text out of diagnostics too.
  • No retries for ambiguous side effects. The host never retries. If a request may or may not have taken effect (a message sent, a toggle flipped), do not repeat it. Retry only an operation that is safe to repeat, once, and only while the time budget allows.
  • Be honest in the message. Say "sent" when you only sent; say "confirmed" only if you checked.

Reference

Declaring dependencies

List what your plugin needs in the manifest, so the user sees it before enabling, and repeat it in the README. Declaring never installs or runs anything.

The requirements list

"requirements": [
  {"kind": "command", "name": "python3", "version": ">= 3.8"},
  {"kind": "command", "name": "hyprctl", "optional": true, "description": "Only the shortcut actions"},
  {"kind": "service", "name": "bluetooth", "optional": true},
  {"kind": "file", "name": "~/.config/sdeck-plus/plugins/hello/token", "description": "Your token, mode 0600"}
]
FieldRule
kindcommand (an executable looked up on PATH), service (a daemon, system service or app) or file (a file the user provides). Required.
name1-64 printable characters. For command a bare name of [A-Za-z0-9._+-], no slash. Required; (kind, name) must be unique.
descriptionUp to 200 printable characters; shown as a tooltip.
versionUp to 32 printable characters, such as >= 3.9. Informational: it is never compared.
optionalBoolean, default false. Mark a dependency optional when only some actions need it.
  • Shown: the plugin's sidebar item has a compact Requires list (kind, name, version, "(optional)", description as a tooltip).
  • Checked: only command entries, by looking for a regular file with an execute bit in each absolute PATH directory. A missing required command shows Missing: <name> as an alert; a missing optional one shows Not found: <name> without an alert. The check repeats on every Update plugins. service and file entries are informational.
  • Never done: the app does not install packages, change permissions, run the commands, start services, or block enabling because of a missing requirement. Your plugin reports its own failures when it runs.
  • In the README, add a ## Dependencies section with the same entries as a table (kind, name, needed for, notes), so people reading the repository see them without the app.

Quality

Testing

Test the plugin by itself first, then with the validator, then in the app.

1. Unit-test the plugin with injected dependencies

Give main its collaborators as parameters, as the template and both reference plugins do: main(argv=None, stdin=None, stdout=None, environ=None), plus an injectable runner or opener for anything that spawns a process or opens a connection. Tests then call main with in-memory streams, a fake environment in a temporary directory and a fake runner that records the argument lists. Assert the exact argv, that no shell is used, the response framing, the request_id echo, every rejected input, and that errors never contain a secret. No test should need the network, a real config directory or the real desktop.

python3 -B -I -m unittest discover -s tests -v

2. Validate the project with the validator

cargo run --offline --example plugin_validate -- <plugin-dir>
cargo run --offline --example plugin_validate -- <plugin-dir> --invoke <action> \
    [--settings '<json>'] [--timeout <seconds>] [--request-id <id>]
  • Without --invoke nothing is run. It copies the project's regular files into a temporary plugin root (no symlinks; at most 256 files, 8 MiB per file and 32 MiB in total; .git and __pycache__ are skipped), opens it with the real host code and prints PLUGIN_VALIDATE_OK: (id, version, protocol, actions with controls and settings, requirements with a PATH check) or one PLUGIN_VALIDATE_ERROR: line per problem. The directory name need not equal the id. The temporary root is always removed.
  • --invoke RUNS your plugin once with your privileges, after printing a warning. It enables the plugin in the temporary root and calls the real host, so the outcome is what the app would see: PLUGIN_INVOKE_OK: with the message, or PLUGIN_INVOKE_ERROR: with the host error. --timeout defaults to 5 seconds (maximum 60) and --request-id to validate-1. Use it only on a plugin you trust and, if the action has side effects, with settings you accept.
  • Exit status: 0 ok, 1 problems or a failed invocation, 2 usage.

3. Try it in the app

Add it with the Add plugin button (see Installing and updating), enable it and assign each action to each control it declares. Use Test action to run it from the editor, then press the real control. Check the status line for the message, the failure texts and a request that exceeds 5 s. A manual test is the only way to confirm what the plugin does to the outside world; the unit tests use fakes. State in your README what you did and did not verify.

sdeck-plus itself guards the template and this page with cargo test --offline --test plugin_sdk.

Using it

Installing and updating

There is no package format. A user adds your plugin from the app, from a folder or an HTTPS repository, or copies two files by hand.

1. In the app: the Add plugin button

  • Where. The icon-only Add plugin button (+) sits in the binding toolbar, immediately left of the Update plugins icon at its right end and always reachable (hover text Add plugin…, accessible name Add plugin). It opens a modal dialog with one entry, Browse… for a folder chooser and Check plugin.
  • What to type. An absolute folder path (/home/you/sdeck-plugin-hello or ~/sdeck-plugin-hello) or an https:// repository address. A relative path is refused. A folder that is, contains or lies inside the app's own plugins folder is refused too: point at the plugin's own project folder.
  • The check comes first. Check plugin (or Enter in the entry) copies the folder, or downloads the repository, into a private temporary folder (mode 0700) and validates it with the same code as plugin_validate: manifest.json rules and its size cap, the executable staying inside the plugin folder, the file limits below, regular files only and no symlinks. Every problem is listed. Nothing is written to the plugins folder, and nothing is installed when any check fails.
  • Requirements only warn. Each command requirement is looked up on the app's PATH. A missing one is flagged Missing: <command> in the preview but never blocks the install; the app never installs anything for the user.
  • The preview. Name, id and version; the source (the folder path, or the repository address with the first 10 characters of the downloaded commit); the number of files and their total size; every action with its controls and settings; the requirements; and a fixed warning that once enabled the plugin runs with the user's privileges and that its code should be read first.
  • Install. The button is available only for a preview of exactly the text in the entry: editing the entry or choosing another folder discards the preview. The plugin is placed in plugins/<id>/ with one atomic rename. Install never enables a plugin: the sidebar shows it as a disabled item and the status line says It is disabled: enable it in the Plugins section. A file with any execute bit is installed as 0755, other files as 0644.
  • Same id already installed: Replace. The preview says so and the button reads Replace; nothing is replaced until the user presses it. Replacing swaps in the new files and disables the plugin, so new code needs a new explicit Enable. If plugins.json cannot be read, nothing is changed.
  • One at a time. Installs are serialised across the whole app: a second one says Another plugin install is already running. Wait for it to finish. Checking and installing run on a worker, so the window stays responsive.
  • Closing cancels. Closing the dialog, or pressing Cancel while a check runs, stops the download and deletes the temporary copy.
  • The app never runs your plugin while checking, previewing or installing, and a missing git or a failed download is explained instead of falling back to anything else.

Repository rules for authors

  • Plugin at the repository root. manifest.json and the executable must be at the top level of the repository. A plugin in a sub-folder cannot be installed from the address; the user would have to download it and give its folder path.
  • HTTPS only, no credentials. The address is https://host/owner/repo (a trailing .git or / is fine) of a repository that needs no login. At most 512 characters, no spaces, no user:password@, no query string or fragment, an ASCII host name with an optional numeric port, and a path of letters, digits and . _ ~ -. ssh://, git@host:path, http://, git://, file:// and every other scheme are refused, and nothing prompts for a password.
  • The system git does the download. git must be installed. The app runs it without a shell as a shallow clone of the repository's default branch: clone --depth 1 --no-tags --single-branch --no-recurse-submodules. Git is configured for no submodules, no hooks (core.hooksPath=/dev/null) and no LFS (the LFS filters are switched off, so LFS content is not downloaded); the user's and the system's git configuration are ignored and credential helpers are disabled. Only the first request may follow a redirect.
  • Bounded. The download has a 60 s deadline and a 32 MiB ceiling that counts .git as well, so a long history can exceed it even when the plugin is tiny. Either limit stops git and removes everything.
  • The commit is shown. The preview names the downloaded commit, so the user can compare it with the repository. Then .git is deleted and the same project limits apply as for a folder: at most 256 files, 8 MiB per file and 32 MiB in total, 8 directory levels, regular files only. A directory or regular file named .git and any __pycache__ directory are skipped.
  • No symlinks. A folder containing a symlink is rejected. In a repository git is told not to create symlinks (core.symlinks=false), so a tracked symlink arrives as a plain text file holding its target; never rely on one.
  • Keep the default branch installable. Only the latest commit of the default branch is fetched. Test that commit with the validator before you push it.

2. By hand: copy the files, enable, update

  • Copy manifest.json and run to <data dir>/sdeck-plus/plugins/<id>/, where the data dir is $XDG_DATA_HOME (absolute) or $HOME/.local/share. The folder name must equal the manifest id, and the executable must keep its execute bit. The folder is shared by every device model. (The app's own install copies the whole project, so ship helper files next to the executable.)
  • Update plugins. The app reads the folder when it starts and when the user presses the Update plugins icon at the right end of the binding toolbar (hover text: Update plugins). Discovery only reads manifests; it never runs anything. Installing from the dialog refreshes the sidebar by itself.
  • Where it appears. Under the Plugins heading of the Actions catalog, each valid plugin is its own collapsible item titled with its name (plus "(disabled)" while off), with the untrusted-code warning, the Enable check box, the Requires list and its actions. A folder that fails validation is listed above the items with the reason. With no plugins the heading shows a hint pointing at the add button and at the plugins folder.
  • Disabled by default. Installing never enables, by either way. Until the user ticks Enable, its actions are listed but cannot be assigned or run. The enabled list lives in plugins.json in the plugin root, written only by the app.
  • Updating. From a repository or folder, add it again and press Replace (the plugin is disabled until enabled again). By hand, overwrite the files and press Update plugins; every run rereads the manifest and the enabled list from disk, so a new run applies at the next press. Bump version whenever the manifest changes. Nothing updates itself.
  • Removing. Delete the folder. The app has no remove button yet. Existing bindings are kept, and the editor says the plugin is not installed until it returns.
  • Not exported. Configuration bundles contain bindings only, never plugin programs, credentials or the enabled list.

Not supported yet

  • Private repositories and SSH. Only public https:// addresses work.
  • Choosing a branch, tag or commit. Only the default branch's latest commit can be installed, so a release tag cannot be pinned from the app.
  • Removing a plugin from the app. Delete its folder by hand.
  • Updating automatically. The user adds the plugin again and chooses Replace.

Planning

Compatibility and versioning

Protocol 1 is the only protocol. The manifest grows by adding optional fields.

What can change under you

  • Protocol 1. protocol_version must be 1 in the manifest, the request and every response.
  • Additive manifest fields. New manifest fields will be optional additions that do not change protocol 1. requirements is the first of them.
  • Older builds reject newer manifests. Because unknown manifest fields are rejected, an sdeck-plus build that predates a field refuses a manifest that uses it, and shows the folder as skipped with the parser's message. If you want to support older builds, leave out optional fields such as requirements and keep the README's Dependencies table.
  • Versioning your plugin. Bump version whenever the manifest changes (new action, field or requirement), note the minimum sdeck-plus version in the README when you use a newer field, and keep action and field ids stable: bindings store them, and a removed action leaves the binding in the "no longer offers" state.
  • This page states today's numbers. Check the changelog when you update the app.

Worked examples

Reference plugins

Two plugins, each its own local Git project (sdeck-plugin-discord and sdeck-plugin-mergbw). No remote repository has been published for either yet.

sdeck-plugin-discord

Three actions: mute and deafen shortcuts sent to the Discord window with hyprctl dispatch sendshortcut (Hyprland), and a message posted as your own bot. Python 3, standard library only.

  • Derives its environment: it finds Hyprland's instance in $XDG_RUNTIME_DIR/hypr/ because the host does not forward the signature.
  • Token file with owner-only permissions, never a setting, never echoed; no retry for the ambiguous send.
  • Bounded time on every subprocess and request.
  • Limits stated: never verified against a live Discord or a real Hyprland session; the tests use fakes only.

sdeck-plugin-mergbw

Writes MeRGBW-style packets to a Bluetooth hexagon light through BlueZ's busctl. Python 3, standard library only.

  • Bounded time: it stops at 4.5 s of the 5 s deadline, so the first press after a pause may fail and the next works.
  • One bounded retry, only for the ATT error 0x0e that is safe to repeat, after a fresh readiness check and only if at least 1 s is left.
  • Fake runner tests stand in for busctl.
  • Records what was verified: on one TG609 only power-off was observed to work; the other packets were accepted but their effect was not reported, and the retry has not been re-tested live.

Lessons from both

  • Derive what the host does not forward instead of requiring user setup.
  • Bound every wait inside the 5 s budget and say what happens on the first slow press.
  • Retry once, and only an operation that is safe to repeat.
  • Test with a fake runner and fake environment, and write down what real-world behaviour you did not verify.
  • Declare requirements, and mirror them in the README's Dependencies section.

Before you share it

Publishing checklist

Short, so you can run through it before every release.

Checklist

  • Repository named sdeck-plugin-<id>, with manifest.json, an executable run, README.md, LICENSE and tests/, all at the repository root so the Add plugin dialog can install it from its https:// address.
  • The repository is public, small (under 32 MiB with its history) and its default branch always holds a version that passes plugin_validate: only that branch's latest commit can be installed today, with no branch or tag selection yet. Tag releases anyway, so users can read what changed.
  • No symlinks, no file over 8 MiB, no more than 256 files; the executable bit is committed.
  • plugin_validate prints PLUGIN_VALIDATE_OK:, and --invoke works for each action you can safely run.
  • Unit tests pass without network, a real config folder or the real desktop.
  • The plugin re-validates every setting, answers exactly one line, echoes request_id and exits 0 for failures.
  • No secret in settings, defaults, messages, stderr or the repository; credentials use a documented owner-only file.
  • Every wait is bounded and fits within 5 s; side effects are never retried blindly.
  • requirements in the manifest and a Dependencies section in the README match.
  • The README states the install steps, the minimum sdeck-plus version, and what you did and did not verify on real hardware or services.
  • version bumped for every manifest change; a license you are comfortable with (the template uses MIT).
